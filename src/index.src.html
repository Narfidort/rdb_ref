    第0章

    リレーショナルデータベースの基礎概念

    なぜ表を分けるのか。主キー、外部キー、ER 図、中間テーブル、CRUD とトランザクション。

    0.1動機：貸出ノートの限界

    図書委員が、本を貸すたびに貸出ノート（紙でも Excel でもよい）へ1行ずつ書き足していく方式で記録していたとする。

    貸出ノート
    貸出日氏名クラス書名著者
    04-10佐藤 花子1-A坊っちゃん夏目漱石
    04-18佐藤 花子1-Bこころ夏目漱石
    04-21佐藤 花子（空欄）吾輩は猫である夏目 漱石
    05-02田中 美咲2-A坊っちゃん夏目漱石
    05-15佐藤 花子1-A坊ちゃん夏目漱石

    1か月後、司書の先生から次のように頼まれた。このノートでは、どれにも正確には答えられない。

    1「夏目漱石の本は何回借りられた？」

    「夏目 漱石」「坊ちゃん」のような書き方の揺れがあり、検索や数え上げで漏れる。毎回手で書くので、揺れはなくならない。

    2「佐藤 花子さんに返却を催促して」

    佐藤 花子は 1-A と 1-B に2人いる。クラスが空欄の3行目は、どちらの貸出か分からない。

    3「羅生門は図書室にある？」

    一度も借りられていない本はノートに一度も出てこないので、蔵書かどうか分からない。

    4「去年のページは捨てていいよ」

    捨てると、そこにしか書かれていなかった本や生徒の情報まで消えてしまう。

    原因は、生徒・本・貸出という別々のものを1冊のノートに混ぜて書いていることにある。実際の図書室では、本にバーコード（本の番号）が貼られ、生徒には生徒証（学籍番号）があり、貸出のときは2つの番号だけを読み取って記録する。名前や書名は、生徒名簿と蔵書リストに1回だけ書かれている。

    students　生徒名簿
    sidPKnameclass
    S01佐藤 花子1-A
    S03佐藤 花子1-B
    S05田中 美咲2-A
    books　蔵書リスト
    bidPKtitle
    B01坊っちゃん
    B03こころ
    B05羅生門
    loans　貸出記録（番号だけを書く）
    lidPKsidFKbidFKloan_date
    1S01B012026-04-10
    3S03B032026-04-18
    6S05B012026-05-02
    8S01B012026-05-15

    こうすると、書名や著者は蔵書リストの1か所にしかないので揺れない（1）。番号で人を区別できる（2）。借りられていない本も蔵書リストにある（3）。古い貸出記録を消しても名簿と蔵書リストは残る（4）。

    このようにものごとの種類ごとに表を分け、番号で表どうしをつなぐ方式でデータを管理するのがリレーショナルデータベース（RDB）である。以下ではその基本的な用語を定義する。

    0.2テーブル・列・行

    定義 0.1（テーブル）table

    テーブルとは、同じ項目（列）をもつ行の集まりである。

    • 列（カラム）：データの項目。列ごとに名前と、入れてよい値の種類（データ型）が決まっている。
    • 行（レコード）：1件分のデータ。各列に値を1つずつもつ。
    students（テーブル）
    sid← 列nameclassnumber
    S01佐藤 花子1-A12
    S02鈴木 一郎1-A15
    S03佐藤 花子1-B12

    色の付いた縦の並びが列 sid、枠で囲んだ横1行が行（生徒1人分）。

    1つのテーブルには1種類のもの（生徒なら生徒だけ）を入れる。値が分からない・まだ無いマスには NULL（ヌル）という特別な印が入る（1.9）。

    0.3主キー：行を1つに決める列

    0.1 の「同姓同名を区別できない」は、行を1つに決める手がかりがないことが原因だった。

    定義 0.2（主キー）primary key

    値を指定すれば行が必ず1つに決まる列（または列の組み合わせ）のうち、その表の代表として1つ選んだもの。主キーの列には重複も NULL も許されない。

    生徒の表では学籍番号 sid が主キーである。氏名は同姓同名がありうるので主キーにできない。2列の組み合わせで主キーにすることもある（例：0.6 の (bid, aid)）。

    理由NULL は「値が分からない」という印なので、NULL の行を「この番号の行」と指すことはできない。

    候補が複数あるとき（学籍番号、メールアドレス、クラスと出席番号の組など）は、途中で値が変わらない・必ず値がある・短いものを選ぶ。SQL では PRIMARY KEY と書く。SQLite では主キーの列にも NOT NULL を書いておく（書かないと NULL が入ってしまう）。

    0.4外部キー：表と表をつなぐ列

    定義 0.3（外部キー）foreign key

    他の表の主キーの値を入れて、その表の行を指す列。入れてよいのは、指す先の表に実際にある値（または NULL）だけである。

    この「指す先が必ず存在する」というルールを参照整合性制約という。

    loans の sid は、students の主キー sid を指す外部キーである。存在しない生徒 S99 への貸出（下の lid=9）は登録できず、貸出記録から指されている生徒 S01 は削除できない。

    loans（指す側）
    lidPKsidFK
    1S01
    2S02
    9S99
    students（指される側）
    sidPKname
    S01佐藤 花子
    S02鈴木 一郎
    S03佐藤 花子
    SQLite は最初、外部キーをチェックしないsqlite3 を起動するたびに PRAGMA foreign_keys = ON; が必要である。設定方法は 2.2 で扱う。

    0.5ER 図と「何対何」

    表と外部キーのつながりを図にしたものが ER 図 である。箱が表、箱の中が列、線が外部キーによるつながりを表す。線の端の記号は、行どうしが何対何で対応するかを表す。

    定義 0.4（カーディナリティ）cardinality

    2つの表の行どうしが「何対何」で対応するか。次の3種類がある。

    種類意味例
    1 対 1どちらから見ても相手は1つ生徒と生徒証
    1 対 N一方から見ると相手はたくさん、もう一方から見ると相手は1つクラスと生徒
    M 対 Nどちらから見ても相手がたくさんありうる生徒と部活（兼部あり）、本と著者（共著あり）
    性質 0.1

    1 対 N のつながりは、N 側の表に、1 側の主キーを指す外部キーを1列置けば表せる。

    理由生徒（N 側）から見るとクラスは1つなので、生徒の各行にクラスの番号を1つ書けば済む。クラス側に生徒の番号を書こうとすると、1つのマスに何十人分も書くことになる。

    0.6多対多と中間テーブル

    本と著者は M 対 N である（1人の著者が何冊も書き、1冊に何人もの著者がいうる）。どちらから見ても相手が1つに決まらないので、性質 0.1 のように外部キーを1列置くだけでは表せない。「1つのマスに著者を並べて書く」「author1, author2 と列を増やす」はどちらも、検索しにくく、人数の上限ができてしまう。

    定義 0.5（中間テーブル）junction table

    「どの本と、どの著者がつながっているか」という組を1行に1つずつ書く表。列は両側の主キー（bid と aid、どちらも外部キー）で、2列の組 (bid, aid) を主キーにする。

    性質 0.2

    中間テーブルの1行と、つながっている組1つ（下の図の線1本）は、過不足なく1対1に対応する（数学でいう全単射）。そして本と中間テーブルは 1 対 N、中間テーブルと著者は N 対 1 である。つまり M 対 N は、中間テーブルを挟むと 1 対 N と N 対 1 に分解できる。

    理由線を1本ずつ1行に書き写したのが中間テーブルで、(bid, aid) が主キーなので同じ線を2回書けない。各行には本と著者の番号が1つずつなので、行から見た相手はそれぞれ1つになる。

    0.7データの操作：CRUD とトランザクション

    ここまでは表の「形」の話だった。ここからは表の中身を「操作する」側の話である。

    定義 0.6（CRUD）create / read / update / delete

    データに対する基本操作は、作る・読む・更新する・削除するの4つしかない。頭文字をとって CRUD（クラッド）という。

    操作SQL図書室の例本資料
    Create（作成）INSERT新しい貸出を記録する1.6
    Read（読み取り）SELECT貸出中の本を一覧する1.7、第3・4章
    Update（更新）UPDATE返却日を書き込む1.10
    Delete（削除）DELETE古い貸出記録を消す2.4

    ところが、意味のある1つの作業が、複数の操作でできていることがある。例えば「S01 が坊っちゃんを返し、その場で S02 が借りる」は、

    1. S01 の貸出記録に返却日を書く（UPDATE）
    2. S02 の新しい貸出記録を作る（INSERT）

    の2つの操作からなる。もし 1 の直後に停電したら、記録上は「本棚にあるはずの本が見つからない」。2 だけが実行されたら「1冊の本を2人が同時に借りている」。どちらも現実と合わない記録が残る。

    定義 0.7（トランザクション）transaction

    複数の操作を「全部実行する」か「何もしなかったことにする」かのどちらかにしかならないようにまとめた、ひとかたまりの処理。

    SQL では BEGIN で始め、COMMIT で確定する。途中でやめたいときは ROLLBACK で開始前の状態に戻す（2.6 で実際に試す）。

    RDBMS はトランザクションについて、次の4つの性質を保証する。頭文字をとって ACID（アシッド）という。

    性質意味図書室の例
    Atomicity
    原子性    		全部実行されるか、まったく実行されないかのどちらか。途中までの状態は残らない。返却と次の貸出の途中で停電しても、どちらか片方だけが記録されることはない。
    Consistency
    一貫性    		制約（主キー・外部キーなど）を破る状態では確定しない。存在しない生徒への貸出を含む処理は確定できない。
    Isolation
    独立性    		同時に実行しても、1つずつ順番に実行したのと同じ結果になる。図書委員2人が同時に同じ本を貸し出そうとしても、二重に貸し出されない。
    Durability
    永続性    		確定（COMMIT）した結果は、直後に電源が落ちても失われない。「貸出を記録しました」と表示された後なら、停電しても記録は残る。

    ACID は、0.1 の貸出ノート（や Excel ファイルを共有して編集する方法）では得られない、RDBMS を使う大きな理由の1つである。銀行の振込（自分の口座から引く・相手の口座に足す）が典型例としてよく挙げられる。

    演習 0-1何対何と表の設計

    次の各組は何対何か。外部キーをどちらの表に置くか、または中間テーブルが必要かも答えよ。

    1. クラスと生徒（生徒はちょうど1つのクラスに所属する）
    2. 生徒と部活（兼部できる）

    解答例

    RDBMS と SQL の役割

    RDB を管理するソフトウェアを RDBMS といい、利用者は SQL という言語で指示を出す。SQL の文は、表の形を決めるデータ定義言語（DDL：CREATE DROP ALTER）、CRUD を行うデータ操作言語（DML：SELECT INSERT UPDATE DELETE）、トランザクション制御（BEGIN COMMIT ROLLBACK）に分けられる。代表例は PostgreSQL、MySQL、Oracle Database、SQLite。本資料の SQLite はサーバを持たず、データベース全体を1ファイルに格納する。SQL は ISO で標準化されているが、製品ごとに対応範囲や独自機能に差がある。

    理論での呼び方

    関係モデル（RDB の理論）では、テーブルをリレーション、行をタプル、列を属性、列がとりうる値の範囲を定義域と呼ぶ。理論上のリレーションは数学の「集合」なので、まったく同じ行が2つあることはなく、行の順番にも意味がない。一方 SQL のテーブルは、主キーがなければ同じ内容の行を何行でも持てる（重複を除く DISTINCT があるのはこのため）。

    スーパーキーと候補キー

    0.3 では「行を1つに決められる列のうち代表を主キーにする」とだけ述べた。この「行を1つに決められる列」は、次のように2段階で整理される。

    定義 0.8（スーパーキー）superkey

    その列（の組み合わせ）の値が分かれば、行が必ず1つに決まるもの。

    {学籍番号} も {学籍番号, 氏名} もスーパーキーである。{氏名} は同姓同名がいると決まらないので違う。「必ず」とは、今のデータでたまたま決まることではなく、規則上これから入るどんなデータでも決まるという意味である。

    定義 0.9（候補キー）candidate key

    スーパーキーのうち、ムダな列を含まないもの。どの列を1つ外しても、もう行が1つに決まらなくなる。

    {学籍番号, 氏名} は氏名がムダなので候補キーではない。{クラス, 出席番号} はどちらか一方では決まらないので、2列そろって候補キーである。主キーは候補キーの中から選ぶ。

    性質 0.3

    スーパーキーに列を付け足してもスーパーキーのままである。だから候補キーかどうかは、列を1つずつ外して、どれを外しても決まらなくなるかを確かめればよい。

    理由学籍番号だけで1人に決まるなら、学籍番号と氏名の両方が分かればもちろん決まる。情報が増えて決まらなくなることはない。

    スキーマとインスタンス

    表の設計図（表名、列名と型、キーなどの制約）をスキーマ、ある時点の中身をインスタンスという。テストに例えれば、解答用紙の枠と、書き込まれた答えである。キーを「今のデータ」ではなく「規則」で決めるのは、キーが中身ではなく枠（スキーマ）の性質だからである。SQL ではスキーマを CREATE TABLE で書き、sqlite3 では .schema で表示できる。

    loans は中間テーブルとどう違うか

    生徒と本の「借りた」というつながりも M 対 N だが、S01 は B01 を2回借りている（lid=1, 8）ので、同じ組 (S01, B01) が2行現れる。loans の1行は「組」ではなく「1回の貸出という出来事」なので、(sid, bid) を主キーにできず、出来事ごとの番号 lid を主キーにしている。貸出日・返却日を持つのもこのためである。

    演習 0-2候補キー（発展）

    表 時間割(曜日, 時限, 教室, 科目, 教員) に次の規則がある。(1) 候補キーをすべて挙げよ。(2) {曜日, 時限, 教室, 科目} はスーパーキーか。候補キーか。

    1. 1つの教室では、同じ曜日・時限に1つの科目しか行わない。
    2. 教員は、同じ曜日・時限に1つの科目しか担当しない。
    3. 各科目の担当教員は1人である（同じ科目を週に複数回行うことはある）。
    解答例

    (1) {曜日, 時限, 教室}（規則1）、{曜日, 時限, 教員}（規則2）、{曜日, 時限, 科目}。3つ目は規則2・3から従う：同じ曜日・時限に同じ科目が2行あれば、規則3より教員が同じになり、規則2に反する。いずれもどの1列を外しても決まらない（{曜日, 時限} だけでは複数の教室で授業がある）。

    (2) {曜日, 時限, 教室} を含むのでスーパーキーである（性質 0.3）。しかし科目を外しても決まるので、候補キーではない。

    演習 0-3中間テーブルの主キー（発展）

    演習 0-1 の club_members について答えよ。(1) 主キーを (sid, club_id) とすると、どんな誤りが防がれるか。(2) 入部日・退部日を記録し、退部した部活への再入部も許すことにした。表をどう変えるべきか。

    (2) 同じ組 (sid, club_id) が入部のたびに現れるので、行は「在籍期間」という出来事になる（loans と同じ状況）。在籍期間ごとの主キー（例：membership_id）を設け、joined_on, left_on 列を追加する。

    1.9NULL の比較

    pages が NULL の本を探すつもりで = NULL と書くと、1行も出力されない。

    sqlite> SELECT * FROM books WHERE pages = NULL;
sqlite> SELECT * FROM books WHERE pages IS NULL;
    定義 1.1（三値論理）

    SQL の条件式は TRUE・FALSE に加えて UNKNOWN の値をとる。NULL を含む比較（NULL = NULL を含む）の結果は UNKNOWN である。WHERE は条件が TRUE の行だけを残す。

    NULL は「値が未知」を表すので、「未知の値が NULL と等しいか」も未知である、と考えれば UNKNOWN になる理由が分かる。NULL かどうかの判定には、比較ではなく専用の IS NULL を使う。同様に、NULL を含む算術の結果も NULL になる（1.10）。

sqlite> UPDATE books SET pages = pages + 10 WHERE bid = 'B05';
sqlite> SELECT bid, title, pages FROM books;

    2.6トランザクション（BEGIN / COMMIT / ROLLBACK）

    0.7 のトランザクションを実際に使う。

    BEGIN;      -- トランザクションを開始する
  …         -- INSERT / UPDATE / DELETE など
COMMIT;     -- 確定する（ここで初めて変更が確定する）
ROLLBACK;   -- COMMIT の代わりに実行すると、BEGIN の前の状態に戻る

    まとめて確定する

    「S01 が坊っちゃん（B01）を返し、その場で S02 が借りる」を1つのトランザクションにする。

    sqlite> BEGIN;
sqlite> UPDATE loans SET return_date = '2026-05-20' WHERE lid = 8;
sqlite> INSERT INTO loans VALUES (9, 'S02', 'B01', '2026-05-20', NULL);
sqlite> COMMIT;
sqlite> SELECT * FROM loans WHERE bid = 'B01';

    取り消す

    BEGIN の後なら、WHERE を付け忘れた DELETE も ROLLBACK で元に戻せる。危ない操作は、BEGIN してから実行し、結果を SELECT で確かめてから COMMIT する習慣をつけるとよい。

    sqlite> BEGIN;
sqlite> DELETE FROM loans;
sqlite> SELECT COUNT(*) FROM loans;
sqlite> ROLLBACK;
sqlite> SELECT COUNT(*) FROM loans;

    途中でエラーが出たら

    次の例では、返却の UPDATE は成功したが、次の INSERT が外部キー制約に反して失敗した（S99 は存在しない）。

    sqlite> BEGIN;
sqlite> UPDATE loans SET return_date = '2026-05-21' WHERE lid = 9;
sqlite> INSERT INTO loans VALUES (10, 'S99', 'B01', '2026-05-21', NULL);
sqlite> ROLLBACK;
sqlite> SELECT lid, return_date FROM loans WHERE lid = 9;
    エラーが出ても自動では取り消されないSQLite では、トランザクションの途中で1つの文が失敗しても、それまでに成功した文（上の UPDATE）は取り消されずに残る。ここで COMMIT すると「返却だけ記録された」状態が確定してしまう。エラーが出たら ROLLBACK すること。なお、COMMIT せずに sqlite3 を終了した場合も、そのトランザクションは取り消される。

    BEGIN を書かずに実行した文は、1文ずつが自動的に1つのトランザクションとして確定している（自動コミット）。1つの UPDATE が途中までしか反映されない、ということは起きない。

    定義 2.1（ビュー）view

    SELECT 文に名前を付けて保存し、表と同じように参照できるようにしたものをビューという。ビューはデータを保持せず、参照されるたびに保存された SELECT 文が実行される。

    CREATE TABLE で作った、実際にデータを保持する表を（ビューと区別して）実表という。ビューを使うと、複雑な問合せを名前で再利用でき、利用者に見せる列や行を限定できる。

    CREATE VIEW view_name [(column, ...)] AS select_statement;

sqlite> CREATE VIEW long_books AS SELECT bid, title, pages FROM books WHERE pages >= 300;
sqlite> .tables
sqlite> SELECT * FROM on_loan;
sqlite> SELECT * FROM long_books;

    ビューは参照のたびに計算されるので、元の表を変えれば結果も変わる。

    sqlite> UPDATE loans SET return_date = '2026-05-20' WHERE lid = 8;
sqlite> SELECT * FROM on_loan;
sqlite> UPDATE loans SET return_date = NULL WHERE lid = 8;

    第3章

    問合せ（1）：並べ替え・集合演算・結合

    SELECT 文の構造、DISTINCT / ORDER BY / LIMIT、UNION / INTERSECT / EXCEPT、直積、内部結合、外部結合

    この章と次の章では、初期状態の library.db を使う（壊した場合は 2.1 の手順で作り直す）。

    3.1SELECT 文の構造

    SELECT [DISTINCT] column_list    -- 5. 出力する列を計算する（重複を除く）
FROM table [JOIN table ON cond]  -- 1. 対象の表を作る（結合）
[WHERE condition]                -- 2. 行を選ぶ
[GROUP BY column, ...]           -- 3. 行をグループにまとめる
[HAVING condition]               -- 4. グループを選ぶ
[ORDER BY column [ASC|DESC]]     -- 6. 並べ替える
[LIMIT n [OFFSET m]];            -- 7. 先頭の n 行を取る

    句は上の順に書く。右の番号は、結果を論理的に計算する順序である。書く順と計算の順が異なるので、例えば SELECT で付けた別名は（計算順で先の）WHERE では原則使えない。

    3.2重複の除去・並べ替え・件数の制限

    DISTINCT は結果から重複行を除く（SQL のテーブルには同じ内容の行が複数ありうる）。

    sqlite> SELECT sid FROM loans;
sqlite> SELECT DISTINCT sid FROM loans;

    ORDER BY は指定した列で並べ替える。ASC（昇順、省略時）と DESC（降順）があり、複数の列を指定すると前の列が等しい行どうしを次の列で並べる。ORDER BY がない場合、行の順序は保証されない。

    sqlite> SELECT title, year FROM books ORDER BY year DESC;
sqlite> SELECT sid, loan_date FROM loans ORDER BY sid, loan_date DESC;

    LIMIT n は先頭の n 行だけを返す。並べ替えと組み合わせて「上位 n 件」を得る。

    sqlite> SELECT title, pages FROM books ORDER BY pages DESC LIMIT 3;
sqlite> SELECT title, pages FROM books ORDER BY pages;

    SQLite では、昇順の並べ替えで NULL は最小の値として先頭に来る。この扱いは RDBMS によって異なる。

    3.3内部結合（INNER JOIN）

    定義 3.1（内部結合）

    2つの表の行の組み合わせ（直積）のうち、結合条件を満たす組み合わせだけを残した表。

    例えば「貸出の sid = 生徒の sid」という条件で結合すると、各貸出記録にその貸出をした生徒の行がくっつく。

    貸出記録に生徒の氏名を付ける。次の3つは同じ結合を表す（3つ目は列 sid が1つにまとまる）。loans AS l は表に別名 l を付ける書き方で、l.sid は「l の列 sid」を表す。

    sqlite> SELECT l.lid, l.sid, s.name FROM loans AS l, students AS s WHERE l.sid = s.sid;
sqlite> SELECT l.lid, l.sid, s.name FROM loans AS l JOIN students AS s ON l.sid = s.sid;
sqlite> SELECT lid, sid, name FROM loans JOIN students USING (sid);
    • 1つ目は直積と WHERE による書き方（定義 3.1 そのもの）。
    • 2つ目は JOIN … ON 条件。結合条件と、行を絞る WHERE を分けて書けるので読みやすい。INNER JOIN と書いても同じ。
    • 3つ目の USING (列) は「同名の列が等しい」という条件の略記で、その列は結果に1つだけ現れる（関係代数の自然結合に相当）。

    3つ以上の表も続けて結合できる。貸出記録に氏名と書名を付ける。

    sqlite> SELECT lid, name, title, loan_date, return_date
   ...> FROM loans JOIN students USING (sid) JOIN books USING (bid);

    M 対 N の関連は、中間テーブルを介した2回の結合で辿る（性質 0.2）。各本の著者名を出す。

    sqlite> SELECT b.title, a.name
   ...> FROM books AS b
   ...>   JOIN book_authors AS ba ON b.bid = ba.bid
   ...>   JOIN authors AS a ON ba.aid = a.aid;

    3.4外部結合（OUTER JOIN）

    内部結合では、結合条件を満たす相手のない行は結果から消える。上の著者名の結果に森鷗外（A06）が現れないのはこのためである。同様に、一度も本を借りていない生徒 S06 は、生徒と貸出の内部結合に現れない。

    定義 3.2（外部結合）

    A LEFT JOIN B は、内部結合の結果に、相手が見つからなかった A の行も残す結合である。残した行の B 側の列は NULL で埋める。

    RIGHT OUTER JOIN は左右を入れ替えたもの、FULL OUTER JOIN は両側について加えたもの（LEFT と RIGHT の和集合）である。OUTER は省略できる。

    sqlite> SELECT s.sid, s.name, l.lid, l.bid
   ...> FROM students AS s JOIN loans AS l ON s.sid = l.sid;
sqlite> SELECT s.sid, s.name, l.lid, l.bid
   ...> FROM students AS s LEFT JOIN loans AS l ON s.sid = l.sid;

    LEFT JOIN の結果では、S06 が loans の列を NULL として現れる。これを利用すると「相手のない行」だけを取り出せる。

    sqlite> SELECT s.sid, s.name
   ...> FROM students AS s LEFT JOIN loans AS l ON s.sid = l.sid
   ...> WHERE l.lid IS NULL;

    解答例 
    sqlite> SELECT b.bid, b.title
   ...> FROM books AS b LEFT JOIN loans AS l ON b.bid = l.bid
   ...> WHERE l.lid IS NULL;

    夏目漱石の本を借りたことのある生徒の sid と氏名を、重複なく求めよ。

    解答例 
    sqlite> SELECT DISTINCT s.sid, s.name
   ...> FROM students AS s
   ...>   JOIN loans AS l         ON s.sid = l.sid
   ...>   JOIN book_authors AS ba ON l.bid = ba.bid
   ...>   JOIN authors AS a       ON ba.aid = a.aid

    集合演算（UNION / INTERSECT / EXCEPT）

    列の数が等しい2つの SELECT の結果を、集合として組み合わせる。結果から重複は除かれる（UNION ALL は除かない）。

    演算結果
    Q1 UNION Q2和集合 Q1 ∪ Q2
    Q1 INTERSECT Q2積集合 Q1 ∩ Q2
    Q1 EXCEPT Q2差集合 Q1 ∖ Q2（順序を入れ替えると結果が変わる）

    生徒 S01 と S05 が借りた本で確かめる。

    sqlite> SELECT bid FROM loans WHERE sid = 'S01';
sqlite> SELECT bid FROM loans WHERE sid = 'S05';
    
    sqlite> SELECT bid FROM loans WHERE sid = 'S01'
   ...> UNION
   ...> SELECT bid FROM loans WHERE sid = 'S05';
sqlite> SELECT bid FROM loans WHERE sid = 'S01'
   ...> UNION ALL
   ...> SELECT bid FROM loans WHERE sid = 'S05';
sqlite> SELECT bid FROM loans WHERE sid = 'S01'
   ...> INTERSECT
   ...> SELECT bid FROM loans WHERE sid = 'S05';
sqlite> SELECT bid FROM loans WHERE sid = 'S01'
   ...> EXCEPT
   ...> SELECT bid FROM loans WHERE sid = 'S05';
sqlite> SELECT bid FROM loans WHERE sid = 'S05'
   ...> EXCEPT
   ...> SELECT bid FROM loans WHERE sid = 'S01';

    演習 3-1 は EXCEPT でも書ける（全部の本から、貸し出されたことのある本を引く）。

    sqlite> SELECT bid, title FROM books
   ...> EXCEPT
   ...> SELECT bid, title FROM books JOIN loans USING (bid);

    直積

    FROM に複数の表をカンマで並べると、各表の行のすべての組合せ（直積）が対象になる。students（6行）と books（6行）の直積は 36 行である。CROSS JOIN と書いても同じである。

    sqlite> SELECT COUNT(*) FROM students, books;
sqlite> SELECT students.name, books.title FROM students CROSS JOIN books;

    直積の大半の行は意味を持たない組合せである。意味のある組合せ（例えば貸出記録に対応するもの）だけを取り出すのが結合である。

    RIGHT JOIN と FULL JOIN

    RIGHT JOIN は左右を入れ替えた LEFT JOIN と同じ結果を与える。FULL JOIN は、例えば著者と著者対応の結合で、どちらにも相手のない行を残す（ここでは外部キー制約により book_authors 側に孤立した行はないので、LEFT JOIN と同じ行になる）。

    sqlite> SELECT a.aid, a.name, ba.bid
   ...> FROM book_authors AS ba RIGHT JOIN authors AS a ON ba.aid = a.aid;
sqlite> SELECT a.aid, a.name, ba.bid
   ...> FROM authors AS a FULL JOIN book_authors AS ba ON a.aid = ba.aid;

    外部結合の条件を ON に書くか WHERE に書くか

    外部結合では、ON の条件は「どの行を相手として結合するか」を決め、WHERE の条件は「結合と NULL の補完が済んだ後の行を選ぶ」。両者は同じではない。「全生徒について、貸出中の貸出だけを結合する」なら、条件は ON に書く。

    sqlite> SELECT s.sid, l.lid FROM students AS s LEFT JOIN loans AS l
   ...>   ON s.sid = l.sid AND l.return_date IS NULL;
sqlite> SELECT s.sid, l.lid FROM students AS s LEFT JOIN loans AS l
   ...>   ON s.sid = l.sid WHERE l.return_date IS NULL;

    1つ目では、貸出中の本がない S02・S05・S06 が lid = NULL として残る。2つ目では、S02・S05 の行（返却済みの貸出と結合された行）が WHERE で除かれて消える。S06 が残るのは、結合で補われた NULL が IS NULL を満たすためで、意図した理由によるものではない。

    演習 3-3FULL JOIN の書き換え

    RIGHT JOIN と FULL JOIN をサポートしない RDBMS（SQLite 3.39 未満など）でも同じ結果が得られるよう、authors FULL JOIN book_authors（上の例）を LEFT JOIN と集合演算で書き換えよ。

    解答例

    FULL JOIN は「左を残す LEFT JOIN」と「右を残す LEFT JOIN（左右を入れ替えたもの）」の和集合である。列の順序をそろえる。

    sqlite> SELECT a.aid, a.name, ba.bid FROM authors AS a LEFT JOIN book_authors AS ba ON a.aid = ba.aid
   ...> UNION
   ...> SELECT a.aid, a.name, ba.bid FROM book_authors AS ba LEFT JOIN authors AS a ON a.aid = ba.aid;
    第4章

    問合せ（2）：集約・副問合せ・ビュー

    集約関数、GROUP BY / HAVING、副問合せ、ビューの活用

    4.1集約関数

    複数の行の値から1つの値を計算する関数を集約関数という。COUNT(*) 以外の集約関数は NULL を無視する。

    関数値
    COUNT(*)行数
    COUNT(x) / COUNT(DISTINCT x)x が NULL でない行の数 / x の異なる値の数
    SUM(x) AVG(x)合計・平均
    MAX(x) MIN(x)最大値・最小値
     
    sqlite> SELECT COUNT(*), COUNT(return_date), COUNT(DISTINCT sid) FROM loans;
sqlite> SELECT COUNT(*), COUNT(pages), SUM(pages), AVG(pages), MAX(pages), MIN(pages) FROM books;
sqlite> SELECT SUM(pages) / COUNT(*) FROM books;

    AVG(pages) は NULL を除いた5冊の平均 1480 / 5 = 296 である。最後の式は NULL の本も分母に数えたうえ、整数どうしの除算なので小数部が切り捨てられる（1480 / 6 = 246.67 → 246）。AS で結果の列に名前を付けられる。

    4.2グループごとの集約（GROUP BY / HAVING）

    GROUP BY 列 は、その列の値が等しい行を1つのグループにまとめ、集約関数をグループごとに計算する。

    sqlite> SELECT sid, COUNT(*) AS n FROM loans GROUP BY sid;

    HAVING はグループに対する条件である。WHERE が集約の前に行を選ぶのに対し、HAVING は集約の後にグループを選ぶ（3.1 の計算順序）。

    sqlite> SELECT sid, COUNT(*) AS n FROM loans GROUP BY sid HAVING COUNT(*) >= 2;
sqlite> SELECT sid, COUNT(*) AS n FROM loans WHERE return_date IS NULL GROUP BY sid;

    結合と組み合わせる。本ごとの貸出回数を、一度も貸し出されていない本も 0 として求めるには、LEFT JOIN と COUNT(l.lid)（NULL を数えない）を使う。COUNT(*) では補われた行も数えて 1 になってしまう。

    sqlite> SELECT b.bid, b.title, COUNT(l.lid) AS times, COUNT(*) AS wrong
   ...> FROM books AS b LEFT JOIN loans AS l ON b.bid = l.bid
   ...> GROUP BY b.bid ORDER BY times DESC, b.bid;

    中間テーブルを介して、本ごとの著者をまとめる。GROUP_CONCAT(x, 区切り) はグループ内の値を連結する SQLite の集約関数である。

    sqlite> SELECT b.title, COUNT(*) AS n_authors, GROUP_CONCAT(a.name, '・') AS authors
   ...> FROM books AS b JOIN book_authors USING (bid) JOIN authors AS a USING (aid)
   ...> GROUP BY b.bid;

    4.3副問合せ

    SELECT 文の中に括弧で囲んで書いた SELECT 文を副問合せという。

    値を返す副問合せ

    結果が1行1列の副問合せは、値として比較に使える。平均よりページ数の多い本：

    sqlite> SELECT title, pages FROM books
   ...> WHERE pages > (SELECT AVG(pages) FROM books);

    IN / NOT IN

    x IN (副問合せ) は、x が副問合せの結果の列に含まれるとき真になる。現在本を借りている生徒と、一度も借りたことのない生徒：

    sqlite> SELECT sid, name FROM students
   ...> WHERE sid IN (SELECT sid FROM loans WHERE return_date IS NULL);
sqlite> SELECT sid, name FROM students
   ...> WHERE sid NOT IN (SELECT sid FROM loans);

    EXISTS / NOT EXISTS

    EXISTS (副問合せ) は、副問合せの結果が1行以上あるとき真になる。次の副問合せは外側の行 s を参照しており、s の各行について評価される（相関副問合せ）。

    sqlite> SELECT sid, name FROM students AS s
   ...> WHERE NOT EXISTS (SELECT * FROM loans AS l WHERE l.sid = s.sid);
    演習 4-1副問合せ
    1. ページ数が最大の本の書名とページ数を求めよ。
    2. 宮沢賢治の本を一度も借りたことのない生徒の sid と氏名を求めよ。
    解答例 
    sqlite> SELECT title, pages FROM books
   ...> WHERE pages = (SELECT MAX(pages) FROM books);
sqlite> SELECT sid, name FROM students
   ...> WHERE sid NOT IN (
   ...>   SELECT l.sid FROM loans AS l
   ...>     JOIN book_authors AS ba ON l.bid = ba.bid
   ...>     JOIN authors AS a ON ba.aid = a.aid
   ...>   WHERE a.name = '宮沢賢治');

    2 では副問合せの l.sid が NOT NULL 制約を持つので、NOT IN の NULL の問題は起きない。

    演習 4-2GROUP BY

    著者ごとの著書数を、著書のない著者は 0 として、著書数の多い順に求めよ。

    解答例

   ...> FROM authors AS a LEFT JOIN book_authors AS ba ON a.aid = ba.aid
   ...> GROUP BY a.aid ORDER BY n_books DESC, a.aid;

    4.4ビューの活用

    結合や集約を含む問合せをビューにすると、以後は表と同じように使える。貸出中の本の一覧と、生徒ごとの貸出回数（0 回を含む）：

   ...> WHERE l.return_date IS NULL;
sqlite> CREATE VIEW loan_counts AS
   ...> SELECT s.sid, s.name, COUNT(l.lid) AS n

   ...> GROUP BY s.sid;

    分散

    SQLite には標準偏差・分散の関数がない。分散は「2乗の平均 − 平均の2乗」（V[X] = E[X2] − (E[X])2）で計算できる。

    sqlite> SELECT AVG(pages * pages) - AVG(pages) * AVG(pages) AS variance FROM books;

    GROUP BY のとき SELECT に書ける列

    標準 SQL では、GROUP BY を使う SELECT の列リストには、GROUP BY の列か集約関数しか書けない（グループ内で値が1つに定まらないため）。SQLite はこの制限を課さず、例えば SELECT sid, MAX(pages) … のような書き方も受け付けるが、他の RDBMS ではエラーになる。

    NOT IN と NULL

    1910 年より後に出た本のどれともページ数が一致しない本を求めるつもりで、次のように書くと結果は空になる。

    sqlite> SELECT pages FROM books WHERE year > 1910;
sqlite> SELECT title, pages FROM books
   ...> WHERE pages NOT IN (SELECT pages FROM books WHERE year > 1910);

    x NOT IN (a, b, NULL) は x <> a AND x <> b AND x <> NULL と同じであり、最後の項が常に UNKNOWN なので、全体が TRUE になることはない（定義 1.1）。副問合せの結果に NULL が含まれうるときは、NULL を除くか NOT EXISTS を使う。

    sqlite> SELECT title, pages FROM books
   ...> WHERE pages NOT IN (SELECT pages FROM books WHERE year > 1910 AND pages IS NOT NULL);

    FROM 句・SELECT 句の副問合せ

    副問合せの結果は表なので、別名を付けて FROM に置ける。また、SELECT の列リストに値を返す副問合せを置ける。

    sqlite> SELECT s.name, c.n
   ...> FROM students AS s
   ...>   JOIN (SELECT sid, COUNT(*) AS n FROM loans GROUP BY sid) AS c ON s.sid = c.sid
   ...> WHERE c.n >= 2;
sqlite> SELECT b.title,
   ...>        (SELECT COUNT(*) FROM loans AS l WHERE l.bid = b.bid) AS times
   ...> FROM books AS b;

    ANY / ALL（SQLite では使えない）

    標準 SQL の x = ANY (副問合せ)（いずれかと等しい）と x <> ALL (副問合せ)（すべてと異なる）は SQLite にない。それぞれ IN、NOT IN で書ける。x > ALL (…) は x > (SELECT MAX(…) …) で書ける。

    sqlite> SELECT title FROM books WHERE pages > ALL (SELECT pages FROM books WHERE year < 1910);

    ビューの更新

    ビューに対する INSERT / UPDATE / DELETE を元の表への操作に一意に翻訳できるのは、一般に、ビューの各行・各列が1つの実表の行・列に対応する場合に限られる。集約・GROUP BY・DISTINCT・集合演算・計算列を含むビューは、ビューの1行が実表の複数行に由来するので更新できない。SQLite は、このような条件にかかわらずビューへの更新をすべて拒否する（トリガーを定義すれば可能）。

    sqlite> UPDATE on_loan_detail SET loan_date = '2026-05-16' WHERE lid = 8;
    演習 4-3ビュー

    返却済みの貸出について、lid、氏名、書名、貸出日数 days（返却日 − 貸出日）を列とするビュー returned_loans を作り、平均貸出日数を求めよ。

    ヒント：julianday('YYYY-MM-DD') は日付をユリウス日（実数の日数）に変換する SQLite の関数である。

    解答例 
    sqlite> CREATE VIEW returned_loans AS
   ...> SELECT l.lid, s.name, b.title,
   ...>        julianday(l.return_date) - julianday(l.loan_date) AS days
   ...> FROM loans AS l JOIN students AS s ON l.sid = s.sid JOIN books AS b ON l.bid = b.bid
   ...> WHERE l.return_date IS NOT NULL;
sqlite> SELECT * FROM returned_loans;
sqlite> SELECT AVG(days) FROM returned_loans;
    演習 4-4総合

    クラスごとに、所属生徒数と、そのクラスの生徒による貸出の総数を求めよ。貸出のないクラスも含めること。

    解答例 
    sqlite> SELECT s.class, COUNT(DISTINCT s.sid) AS n_students, COUNT(l.lid) AS n_loans
   ...> FROM students AS s LEFT JOIN loans AS l ON s.sid = l.sid
   ...> GROUP BY s.class;

    結合により生徒の行は貸出の数だけ複製されるので、生徒数は COUNT(*) ではなく COUNT(DISTINCT s.sid) で数える。

    ; を打っても ...> のまま引用符 ' または " が閉じていない。閉じ引用符を打ってから ; を打つ（エラーになって入力待ちに戻る）。
    quit と打ったら ...> になったドットコマンドは先頭の . が必要。; を打ってから .quit。
    no such table: …表名の誤り、または別のデータベースファイルを開いている。.tables と .databases で確認する。
    UNIQUE constraint failed: …主キーまたは UNIQUE 列の値が既存の行と重複している。同じ INSERT を2回実行していないか確認する。
    NOT NULL constraint failed: …NOT NULL 列に値を与えていない。
    FOREIGN KEY constraint failed参照先に存在しない値を入れようとした、または参照されている行を削除しようとした（2.2）。
    near "…": syntax error示された語の直前付近に文法の誤り。全角文字・全角空白、カンマの過不足、句の順序（3.1）を確認する。
    日本語が文字化けする端末の文字コードが UTF-8 であることを確認する。

    上で解決しない場合は 困ったとき の方法で AI に質問する。
